工作场景

支付系统账户表，MySQL 8.0.28，RR 隔离级别（默认）。周一上午批量代扣任务上线 10 分钟，在线转账开始报 1213（Deadlock found），5 分钟内 200 多次。代码一眼见病灶：代扣按导入文件顺序逐个 UPDATE 账户，一个事务包 500 户；转账事务按用户操作顺序先扣 A 再转 B——同一批账户、相反的加锁顺序。可选路径：

  • A. 捕获 1213 自动重试，重试成功就当无事发生
  • B. 固定加锁顺序：所有写入口统一按账户 ID 升序
  • C. 缩短事务：把事务里的风控 RPC、短信通知移出去
  • D. 隔离级别降到 RC，从根上减少 gap lock

判断框架

第一步 · 约束

金融账务一笔不能错：重试必须幂等，余额扣减不能重扣；MySQL 8.0.28，RR 是全司统一口径，动隔离级别要重审主从复制与对账的语义假设；批量代扣必须当日跑完，不能靠降频逃避。诊断手段只有 SHOW ENGINE INNODB STATUS——且它只保留最近一次死锁。

第二步 · 关键认知

死锁不是事故，是 InnoDB 的自我保护：wait-for graph 检测到等待环，主动回滚代价小的事务让另一个活——好过互相耗到 innodb_lock_wait_timeout（默认 50 秒）。所以目标从来不是零死锁，而是低频、可重试、不伤业务。判读 LATEST DETECTED DEADLOCK 段，把两个事务各持有什么锁、等什么锁的时序重建出来——疗法是照着时序开的，不是背的。

第三步 · 选项与代价

A 重试必须有但只是兜底：高频死锁下重试风暴放大流量，还掩盖病根。B 固定顺序治本——所有入口按账户 ID 升序，死锁退化为排队；代价是要梳理这张表的全部写路径（含三个月后新同事写的），纪律成本高。C 短事务把锁窗口从 780ms（事务里夹着风控 RPC 超时重试）压到 8ms，交错概率同步降两个量级；代价是通知、流水要改成事务外或异步。D RC 能消掉大部分 gap lock（RC 下普通当前读只剩记录锁），但金融语义重审的面太大。

第四步 · 押注与复盘

押 B+C，这是事务边界的业务改写而不是调数据库参数：代扣任务重写为“读入后按账户 ID 排序、每 50 户一个小事务”；转账双账户更新强制小 ID 在前；风控 RPC 和短信移出事务，账务事务里只剩三条语句。重试做兜底：捕获 1213、幂等键防重扣、最多 3 次退避。上线后死锁从日均 200+ 降到 0~2 次，残留全被重试吃掉。同时开 innodb_print_all_deadlocks=ON 把每次死锁写进 error log——status 只留一份，看不了趋势。

被否决选项的胜场

这次没降 RC，但 RC 在很多场景就是正解：高并发插入的消息表、秒杀扣减，gap lock 造成的互锁远大于幻读风险，不少互联网公司的核心库就跑在 RC（阿里规范甚至默认 RC）。反过来 RR 的 gap lock 也不是缺陷——它正是防幻读的实现，金融对账里 SELECT ... FOR UPDATE 锁住空范围防插入，靠的就是它（行锁加 gap lock 合称 next-key lock）。否决 D 的理由不是 RC 不好，是全司隔离级别统一这个约束下，改语义的审批与重审成本远超改代码。

面试怎么答

面试官的三种问法

  • “讲一次你排查死锁的完整过程。”（金融/支付岗必问，考日志判读不是背概念）
  • “RR 和 RC 你们线上用哪个？为什么？”（考隔离级别语义与工程取舍）
  • “gap lock 什么时候出现？怎么避免？”（深水区，区分背过和踩过）

好回答的结构

先一句话定性（死锁是保护不是事故，目标是低频可重试），再讲日志判读 → 时序重建 → 三疗法选择，最后一定带重试兜底和幂等。能把“改业务事务边界”说成主修复手段的，是高级信号。

60 秒示范：“批量代扣上线 10 分钟，转账开始报 1213，5 分钟 200 多次。我先 SHOW ENGINE INNODB STATUS 重建时序：代扣按文件顺序、转账按用户操作顺序更新同一批账户，方向相反各持一行锁互相等。修复不是调数据库参数，是改事务边界：代扣重写成按账户 ID 排序、每 50 户一个小事务，原来 500 户一个大事务；转账双账户强制小 ID 在前；风控 RPC 移出事务后锁窗口从 780ms 压到 8ms。重试兜底：捕获 1213、幂等键防重扣、最多 3 次。死锁从日均 200+ 降到 0~2。降 RC 我评估过没做——它对高并发插入场景是对的，但我们要重新审计全司的隔离级别语义和对账假设，代价不成比例。”

翻车回答

  • “死锁是数据库 bug，把锁超时调大就好”——把保护机制当故障，方向全反。
  • 只会“捕获异常重试”——兜底当主疗法，面试官立刻追“重试风暴怎么办”。
  • gap lock 说不出触发条件（RR、非唯一索引范围、不存在行的当前读）——深水区直接沉底。

AI 破绽自查：AI 能背三疗法，但给不出“锁窗口从 780ms 压到 8ms”这种从自己日志里读出来的数字，也说不清“我们当时没降 RC”的组织语境。

追问链

先自己心里答 10 秒，再展开对照。

追问一：两个事务都没更新到任何行，为什么也死锁？

考察意图：gap lock 与插入意向锁的现场推演——RR 深水区的送命题。

答到什么程度算过关：能一步步推：表里 id=90 不存在，区间 (80, 100) 是 gap。T1 执行 SELECT ... FOR UPDATE WHERE id=90（当前读，没匹配到行）锁住该 gap；T2 同样语句锁同一个 gap——gap 锁彼此兼容；随后 T1 INSERT id=90 需要插入意向锁，被 T2 的 gap lock 挡住；T2 也 INSERT，被 T1 挡住——环成立。解法方向：去掉“先探测再插入”改直接插入吃唯一键冲突；或该表评估 RC（RC 下不匹配行的当前读不加 gap lock）。能自己画出这个时序，才算踩过。

追问二：InnoDB 怎么知道死锁发生了？检测本身有代价吗？

考察意图：从使用者跨到理解实现——热点行场景的取舍。

答到什么程度算过关：wait-for graph：锁等待构成有向图，出现环即死锁，回滚 undo 量小的事务（innodb_deadlock_detect 默认 ON）。代价：每次锁等待都要维护并检测图，热点行上大量线程排队时，检测本身能把 CPU 打满——秒杀场景经典问题。5.7.15+ 提供开关，8.0 延续：确认死锁率低且客户端有重试时可以 SET GLOBAL innodb_deadlock_detect=OFF，靠 innodb_lock_wait_timeout 兜底。能讲清“关检测省 CPU、换超时和重试兜底”这对交换，过关。

追问三：为什么死锁告警阈值不该设成一次就报？

考察意图：运维手感——真处理过死锁的人分得清信号和噪音。

答到什么程度算过关：死锁在并发系统里是统计必然，修复后残留 0~2 次/日属于背景噪音，为它继续加约束只会增加复杂度。告警看两个信号：绝对阈值（如 5 分钟超 20 次）和趋势突变（基线 2 次/日突然 50 次，说明新的交错模式进来了——常见是新批处理或新入口没按约定顺序加锁）。点题：告警是给“变化”的，不是给“存在”的。
