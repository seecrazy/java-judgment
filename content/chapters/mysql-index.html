工作场景

订单表 1.2 亿行，MySQL 8.0 主从。周三下午运营反馈后台列表“翻不动了”，慢日志里 SELECT * FROM orders WHERE status=2 ORDER BY id DESC LIMIT 10000000, 20——第 50 万页——跑了 8.2 秒：offset 要沿索引产出 1000 万行再丢掉。这条查询打满从库 IO，报表服务一起被拖下水。而 (status, id) 联合索引本来就躺在表上。可选路径：

  • A. 继续加索引：建一个覆盖列表全部字段的联合索引
  • B. 纯 SQL 改写：延迟关联，先查 id 再回表取那 20 行
  • C. 业务改写：列表改游标翻页，全量导出改异步任务
  • D. 运营查询限流 + 独立从库，先隔离再说

判断框架

第一步 · 约束

主库写入 SLA：P99 50ms 不能动，白天峰值 4500 写 QPS；运营列表日均使用 200 次，是低频后台需求；从库同时服务报表，不能被单条大查询独占。改交互要产品排期，一周内能动 SQL 和配置——这是“技术侧先止血、业务侧跟上”的典型约束组合。

第二步 · 关键认知

explain 判读有固定次序：type → rows → Extra。这条 SQL 的 explain 是 type=ref、rows≈1000 万、Extra=Using index——优化器没选错，(status, id) 已经免回表地按 id 倒序吐数据；问题是 offset 语义要求它产生并丢弃前 1000 万行。这是“有没有索引”和“该不该这么查”的分界线：索引救不了访问模式。

第三步 · 选项与代价

A 覆盖索引要塞进列表全部 12 个字段，索引比表还宽：主库每秒 4500 次写入全部背上写放大，等于拿主链路的钱买后台的爽。B 延迟关联把回表压到 20 次，但沿二级索引数 1000 万行免不了，8 秒变 4 秒，没有质变。C 游标翻页 WHERE id < last_id ORDER BY id DESC LIMIT 20 直接定位，毫秒级；代价是“跳到第 N 页”没了，要和产品谈。D 治标：隔离该做，但查询本身是错的这一点没变。

第四步 · 押注与复盘

押 C：列表改游标 + 筛选条件收窄，全量导出改异步任务走独立从库。三天上线，列表接口从 8.2s 到 6ms；导出进队列后从库 IO 峰值降 60%。顺手用 sys.schema_unused_indexes 挖出 3 个半年没人用的索引删掉，主库写入 P99 从 45ms 回到 28ms——删索引比加索引更需要证据，写放大的账平时没人算。

被否决选项的胜场

这次否决了“再加索引”，但加索引在另一种场景就是正解：C 端高频链路的等值查询（用户查自己的订单），一个区分度高的 (user_id, status, created_at) 联合索引是教科书答案——高频、读多写少、字段收敛，写放大换查询延迟是划算的。延迟关联也不是废物：offset 在十万级以内、交互不能动的场景，它是不改业务的纯 SQL 最优解。否决它们不是它们错，是这次的病灶在访问模式，不在索引结构。

回到工位

明天上班三步，对着你们自己的慢日志：

  1. 确认慢日志阈值：long_query_time 默认 10 秒太宽，调到 0.5，再用 pt-query-digest 取 Top 3 慢 SQL。
  2. 逐条 EXPLAIN，按 type → rows → Extra 次序判读，对号入座：
    explain 特征含义第一动作
    type=ALL、rows≈全表全表扫描补/改索引，先查失效三件套：函数包裹列、隐式类型转换、前导 %
    type=ref/index 但 rows=offset 量级索引没选错，访问模式错了游标 / 延迟关联 / 异步导出，停止堆索引
    Using filesort排序没吃到索引联合索引重排：等值列在前、区分度高者优先、排序列殿后
    Using index覆盖索引免回表算写放大的账，确认值这份数据拷贝
  3. 跑 sys.schema_unused_indexes 和 sys.schema_redundant_indexes，拿候选删减名单找 DBA 复核（观察期要覆盖月结和大促回溯，唯一约束索引除外）。要问产品的一句话：“这个列表真的有人翻到第 50 万页，还是其实只想要筛选和导出？”——这一句决定你花两天改交互，还是花两个月堆索引。

面试怎么答

面试官的三种问法

  • “explain 你主要看哪几个字段？”（一面标配，考判读次序，不是背全字段）
  • “列表页翻到几十万页很慢，怎么办？”（考深翻页的三层解法与取舍）
  • “你们线上索引怎么治理？”（高级岗分水岭：敢不敢删、怎么算写放大）

好回答的结构

先给判读次序（说明有方法论），再讲“索引已最优但访问模式错误”这个案例，落到业务改写和索引治理两个动作。索引失效清单放最后当补充，不当主菜。

60 秒示范：“1.2 亿行订单表，后台列表 LIMIT 10000000, 20 跑 8.2 秒拖垮从库。我先 explain：type=ref、Extra=Using index——索引已经最优，(status, id) 免回表，问题是 offset 要产生并丢弃 1000 万行，这不是索引能救的。所以答案是业务改写：列表改游标 where id < last_id，6ms 返回；全量导出改异步走独立从库，从库 IO 峰值降 60%。加宽索引我评估过没做——为日均 200 次的后台查询，让主库 4500 写 QPS 背 12 个字段的写放大，不划算。事后还删了 3 个没人用的索引，主库写入 P99 从 45ms 降到 28ms。”

翻车回答

  • 把“索引失效十大场景”背三分钟——那是清单不是判断，面试官立刻追问“失效之外呢”。
  • 深翻页只答“加索引”或“加缓存”——等于承认没 explain 过这条 SQL。
  • “索引越多越好”或反之——两个方向都没算写放大的账，都是拍脑袋。

AI 破绽自查：AI 会把游标、延迟关联、覆盖索引各写一段谁也不得罪。你的回答必须有“我们选了哪个、没做哪个、写入 QPS 是多少”。

追问链

先自己心里答 10 秒，再展开对照。

追问一：联合索引 (status, id) 明明存在，为什么深翻页还是慢？

考察意图：分清“索引选错”和“访问模式错误”——本章的核心分界线。

答到什么程度算过关：能讲出执行路径：二级索引按 (status, id) 有序且 Using index 免回表，但 offset 1000 万意味着引擎必须沿索引产出 1000 万零 20 条再丢掉前面——扫描量由语义决定，不是优化器选错。解法只剩两类：减少扫描（游标把定位变成 B+ 树一次下沉，O(log n + n)）或减少产出（延迟关联把回表压到 20 次但数行免不了）。能补一句“rows 是采样估算，真实行数用 8.0.18+ 的 EXPLAIN ANALYZE 对比”更好。

追问二：删索引你怎么敢的？怎么证明它没在用？

考察意图：写放大量化与变更安全——敢删，且删得有依据。

答到什么程度算过关：证据链三层：performance_schema.table_io_waits_summary_by_index_usage（或 sys.schema_unused_indexes）观察至少一个完整业务大周期，含月结和大促；redundant 检查是否被更长联合索引的左前缀覆盖；先从库后主库、留回滚 DDL。代价侧要能报数：每个二级索引是一份独立数据拷贝，写入要维护全部索引，buffer pool 还得装下它们的热页——我们删 3 个，写入 P99 从 45ms 到 28ms。再声明边界：唯一索引和约束索引不进删减名单。

追问三：游标翻页的代价是什么？产品非要“跳到第 N 页”怎么办？

考察意图：知道每个方案的边界，且能把技术约束翻译成产品语言。

答到什么程度算过关：三个限制：只能顺序翻；续拨字段必须唯一且稳定（不唯一就 (sort_col, id) 双条件续拨）；按非索引字段排序时游标失效。产品坚持跳页的组合拳：跳页场景交 ES 或搜索服务（本来就不该拿 MySQL 干）；或限制最大页数——Google 也只给几十页。点题一句：这不是妥协，是把“无限深翻页”这个伪需求拆穿——没人真翻到第 50 万页，用户要的是筛选和导出。

追问四：explain 的 rows 和真实执行行数差了 10 倍，怎么回事？

考察意图：统计信息认知——优化器不是神，以及 8.0 的修法。

答到什么程度算过关：rows 是基于采样页的基数估算不是实测；表大、数据倾斜、大批量导入后都会飘。动作顺序：ANALYZE TABLE 重采样；倾斜列用 8.0 直方图（ANALYZE TABLE ... UPDATE HISTOGRAM ON 列）帮优化器；仍选错索引才考虑 force index，并留注释说明统计信息背景。能把“先修统计信息再改 SQL”这个顺序说成纪律，过关。
