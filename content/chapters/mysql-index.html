这一章要解决的生产问题

运营后台导出列表，翻到 50 万页时一条 SQL 跑 8 秒拖垮从库。索引都建了——问题不在“有没有索引”，在访问模式本身。

写作中

本章正在按样板章结构写作。计划覆盖的判断点：

  • explain 判读次序：type → rows → Extra（Using filesort / Using index）——先判断“优化器想干什么”再动手
  • 深翻页的正确解：游标（where id > last_id limit n）、延迟关联、覆盖索引——业务改写常常优于索引堆砌
  • 联合索引的最左原则与区分度排序；索引失效清单（函数、隐式转换、前导 %）之外——“索引太多”的写放大代价
  • 被否决选项的胜场：为运营低频查询建索引拖累主链路写入时，“从库+错峰”比索引更对
  • 面试信号：敢说“我们删了三个没用的索引，写入 P99 降了”就是经历过的人
