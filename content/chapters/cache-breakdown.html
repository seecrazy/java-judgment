工作场景

周五晚高峰，商品详情页 DB 连接池突然耗尽，整站雪崩 4 分钟。复盘定位：当日热门单品的缓存到期，同一瞬间约 2.8 万 QPS 的同一主键查询直落 MySQL——库本身扛得住，连接池先死。可选路径：

  • A. 热点 key 永不过期，更新走后台任务
  • B. 互斥锁重建：只放一个请求去查库，其余等或读旧值
  • C. 逻辑过期：value 里带过期时间，过期后返回旧值 + 异步刷新
  • D. 前面再加一层本地缓存（Caffeine）

判断框架

第一步 · 约束

读多写少（约 5000 : 1）。对“旧数据”的容忍度分字段：文案可以旧 1 分钟，价格不能旧超过 10 秒，库存要准。夜间还有批量改价任务——这意味着“永不过期”对价格字段是灾难。先把这些问清楚，选型其实已经被约束推完了。

第二步 · 关键认知

穿透 / 击穿 / 雪崩是三个不同的问题模型：不存在的 key（要挡无效请求）、热 key 过期瞬间（要收敛重建）、集体过期或实例故障（要隔离与熔断）。解法不能互换，因为它们防的不是同一个故障。面试时把三者混答，等于暴露没有故障模型。

第三步 · 选项与代价

B 把并发收敛到 1，DB 永远只有一个查询，代价是锁的实现复杂度（超时、重试、死锁）与等待延迟——适合“旧数据完全不可接受”的场景。C 用“短暂的旧”换“永不击穿”，代价是业务必须显式接受 staleness——这不是技术能替业务决定的。A 对配置字典类是正解，对会被并发修改的数据（价格、库存）会放大一致性问题。D 便宜有效，但多实例间本地缓存不可控，只能给 1~2 秒的极短 TTL 且要白名单控制。

第四步 · 押注与复盘

组合拳：主路径 C（逻辑过期 + 异步刷新），文案类字段上 A，Top 热点单品叠加 D（本地缓存 1~2 秒，白名单）。同时给 DB 侧兜底：连接池上限按“Redis 全失效时 DB 也只是变慢而不是雪崩”倒推，查询侧加熔断。复盘沉淀：缓存方案评审必须先问业务一句话——“旧多久可以接受？”答不出这个问题就不该定 TTL。

被否决选项的胜场

互斥锁在“写后必须立刻读到新值”的强一致读场景（审批状态、风控名单）仍是首选——它牺牲吞吐换一致。永不过期 + 后台刷新在字典、配置、类目树上就是标准答案。这次不选它们，是因为商品详情的数据特征和一致性需求不同，不是它们不好。

回到工位

三步，给你的缓存体系做一次体检：

  1. 找出 TTL 最短的 10 个 key（监控面板或 redis-cli --scan + TTL 抽样），逐个问业务方“旧 X 秒可以吗”，把答案记进设计文档——多数击穿事故的根因是从来没人问过这句话。
  2. 圈出“高 QPS + 短 TTL + 单 key”的组合——这就是你的击穿候选名单，对照上面决策树逐个定方案。
  3. 确认降级路径：Redis 整个挂了，查询侧有熔断吗？DB 连接池的 maxActive 是按“缓存全失效”的水位倒推的吗？不是的话，今天就是改的日子。

面试怎么答

面试官的三种问法

  • “穿透、击穿、雪崩分别怎么防？”（一面标配，考分类）
  • “这些解法为什么不能混用？”（二面，考故障模型）
  • “你们的缓存一致性怎么保证的？”（顺着击穿往深挖的前奏）

好回答的结构

先分清三个问题模型（各一句话），再按业务容忍度选解法，最后一定补一句兜底（熔断 / 多级 / 连接池水位）。“防”和“兜底”是两层，只有防没有兜底的方案在面试官眼里是裸奔。

60 秒示范：“我们详情页出过一次击穿：热门单品缓存到期，2.8 万 QPS 同一瞬间直落 DB，连接池先耗尽，整站雪崩 4 分钟。修复不是简单加 TTL：先把‘旧多久可接受’按字段问清楚——文案可以旧 1 分钟、价格 10 秒内；主路径用逻辑过期加异步刷新，永不击穿但接受短暂旧值；文案类直接永不过期走后台刷新；Top 热点再叠 1~2 秒本地缓存白名单。DB 侧同时把连接池上限按‘缓存全失效’水位倒推并加熔断。互斥锁我评估过没做主路径——它是‘一点旧都不可接受’场景的解，我们的业务约束没那么硬。”

翻车回答

  • 三个概念定义互相串、解法互相借——一问“布隆过滤器防什么”就露馅（防穿透，不防击穿）。
  • 只答 Redis 侧，不答 DB 兜底——缺半边。
  • “把 TTL 加随机值打散”——那是雪崩的解法，答在击穿上就是没分清问题模型。

AI 破绽自查：AI 会把所有解法各写一段不押注。真实工程师的答案里必须有“我们主路径用了哪个、没做哪个、为什么”。

追问链

先自己心里答 10 秒，再展开对照。

追问一：如果挂的不是这个 key，是 Redis 整个实例呢？

考察意图：从单点故障升级到集体故障，看你有没有“防与兜底分层”的体系感。

答到什么程度算过关：这是雪崩模型：集体过期 / 实例故障时，问题不是“怎么重建”，而是“怎么让 DB 活到重建完成”。答出四层：熔断限流（查询侧先降级，宁可拒绝部分请求）、多级缓存（本地缓存此时是救命的）、持久化与高可用架构（主从 + 哨兵 / 集群）、预案演练。点题一句：击穿靠收敛，雪崩靠隔离——两类故障的处理哲学不同。

追问二：互斥锁方案里，为什么不用 ZooKeeper？

考察意图：分布式锁选型边界，以及“锁保护的操作是否幂等”这个前置判断。

答到什么程度算过关：先给前置判断：缓存重建是幂等操作——锁弱一点（两个请求同时重建）后果只是浪费一次查询，不会出错。所以选锁看的是成本与复杂度：ZK 强一致但重（会话、临时节点、羊群效应），Redis 锁（Redisson）轻但要看超时与 RedLock 争议。对幂等临界区，选轻的；对非幂等临界区（扣库存、转账），锁本身再强也不够，要幂等键 + fencing token 或数据库层约束。把“先问幂等再选锁”说出来，这题就是送分变加分。

追问三：热点 key 把 Redis 单个分片打满怎么办？

考察意图：是否理解 Redis 分片的物理边界——这题区分“用过 Redis”和“运维过 Redis”。

答到什么程度算过关：单个 key 只会落在一个分片（slot），集群扩容救不了热点。解法三层：本地缓存挡在最前（对本章就是 D 方案）；热点副本——key 加后缀打散成 N 个副本随机读，写时全写；客户端路由层做热点探测与就近读。再补一句代价：“副本打散把一致性窗口放大 N 倍，所以只配读多写少的数据”——能说代价，才是高级。
