工作场景

大促主场：1,000 件库存的商品，运营预估 50 万人抢。评审会上每层都在喊不够强——网关说扛不住、DB 说单行锁、Redis 说热点 key。架构师该说的第一句话是："99.8% 的请求注定失败，要讨论的是让它们死在哪一层。"可选路径：

  • A. 按峰值流量全链路扩容
  • B. 漏斗减法：前端 / CDN / 网关 / Redis 预扣 / 异步下单层层砍流量
  • C. 排队发号：先到先得，按库存量放行进下单页
  • D. 不改架构，DB 乐观锁 where stock > 0 硬扛

判断框架

第一步 · 约束与量级估算

指标量级推导
开抢瞬间峰值约 5 万 QPS50 万人开抢后 10 秒内涌入刷新
真实下单点击约 5,000 QPS按 10% 用户点击下单估
库存1,000 件成功请求上限就是 1,000，含回补重试
注定失败99.8%(50,000 − 1,000) / 50,000
DB 目标写入两位数 TPS按库存数量级收敛后的落库水位

约束三条：不能超卖（资损红线）、少卖要有界（业务指标）、一人一单（历史大促约 30% 请求来自重复账号）。这组数字直接改写问题：目标不是"系统扛住 5 万 QPS"，而是"99.8% 的请求在离用户最近的地方被礼貌拒绝"。

第二步 · 选项与代价

漏斗每层的砍法与砍量：前端按钮置灰 + 倒计时 + 验证码，把 5 万 QPS 在时间上摊开、把脚本党挡在最外层；秒杀页全静态上 CDN，动态的只剩库存数接口，页面流量不过源站；网关令牌桶按库存的 2 倍（2,000 QPS）放行——放多了白放，放少了误伤真实手快的人；Redis Lua 预扣把"判库存 + 判一人一单 + 扣减"做成一个原子脚本，只放 1,000 个成功；MQ 异步下单，DB 按自身水位消费，落库压力从 5,000 TPS 收敛到两位数。

库存不超卖要三道防线，少一道都有对应事故：第一道 Redis Lua 原子预扣挡量——没有它 DB 直接死；第二道 DB 条件更新 UPDATE stock SET n = n - 1 WHERE id = ? AND n > 0，看影响行数——Redis 与 DB 之间任意时刻崩机都不超卖、只可能少卖；第三道对账兜底：Redis 剩余、DB 实扣、订单数三方核对，把"预扣了没下单、下单了没落库"的少卖找回来回补。三道防的是三类不同的坏，不能互相替代。

热点行拆分（1,000 件拆 10 段各 100）这次评估了没做：1,000 次 UPDATE 落同一行，行锁串行一秒内完成，远未到瓶颈；而分段的全局精确余量要 SUM、退货回补要记段号、段间不均要做借段。它的出场条件是落库 TPS 到千级、单行锁等待成为可见瓶颈。

第三步 · 押注

选 B 漏斗，叠加 C 的轻量版（网关层排队页做降级体验）。押注声明：没做 A 全链路扩容，为注定失败的 99.8% 买机器是纯浪费；没做热点行分段，量级不匹配；没做 D 乐观锁硬扛，5,000 TPS 的条件更新会把 DB 连接池与行锁队列一起打爆。回补链路全部带幂等键——取消订单回补库存重复执行一次，就是反向超卖。

第四步 · 复盘

实测数字：网关拦掉 96% 请求，DB 峰值写入 87 TPS，零超卖，少卖 3 件（支付超时回补延迟，对账 2 分钟内找回）；一人一单集合拦下 1.2 万次重复请求。沉淀两条流程：秒杀评审必须先交"库存 / 预估流量 / 放行倍数"三个数；大促前跑一次故障注入——预扣成功后 kill 消费者，验证对账能找回。

被否决选项的胜场

全链路扩容在"库存与流量同量级"的常态化抢购（库存 10 万件的日常秒杀场）是对的——那时砍流量等于砍收入，漏斗哲学的前提就是库存远小于流量。排队发号在强公平性场景（票务、新股申购）是主案：先到先得写进产品规则，系统只需按号放行；我们没做完整版，因为电商用户要"立刻知道结果"，排队页只做降级体验。乐观锁硬扛在内部低并发场景（几百 QPS、库存几十）就是全部答案，一行 SQL 顶一套架构。

回到工位

下次秒杀评审，带这三样进场：

  1. 放行倍数表：每层放行阈值与库存的关系写清楚（网关 = 库存 × 2，Redis 预扣 = 库存 × 1）。倍数拍脑袋的场次，就是超卖或误伤的场次。
  2. 问业务一句话："超卖和少卖，哪个更不可接受？退货回补窗口多长？"——第一个答案决定防线投入，第二个决定回补幂等的 TTL。
  3. 故障注入清单：预扣后 kill 消费者、扣减后订单超时、回补消息重发——三针打完不超卖不少卖，兜底才算闭环。

面试怎么答

面试官的三种问法

  • "设计一个秒杀系统。"（保留曲目，考减法叙事）
  • "库存超卖怎么防？"（考防线分层的完整性）
  • "流量是库存的 500 倍，DB 怎么活？"（考收敛思维）

好回答的结构

反问两个数（多少库存、多少预期流量）→ 用"99.8% 注定失败"定调 → 漏斗自外向内每层砍多少、按什么规则 → 三道防线各防什么坏 → 对账与回补幂等收尾。

60 秒示范："先对数：1,000 件库存、预估 50 万人、开抢峰值约 5 万 QPS——99.8% 的请求注定失败，所以设计目标是层层做减法。前端验证码摊开时间，页面静态上 CDN；网关令牌桶按库存 2 倍放行 2,000 QPS，其余直接拒；Redis Lua 把判库存、判一人一单、扣减做成一个原子脚本，只放 1,000 个成功进 MQ；DB 条件更新 where stock 大于 0 兜底，最后对账把少卖找回来。实测网关拦掉 96%，DB 峰值 87 TPS，零超卖。热点行分段我评估过没做——1,000 次行锁更新一秒内完成，分段是千级落库 TPS 才值得的复杂度；全链路扩容也没做，为注定失败的流量买机器是浪费。"

翻车回答

  • 上来画架构图，不问库存和流量——没有数字就没有减法比例，全是套路。
  • "Redis 扣库存就不会超卖"——Redis 与 DB 之间任何故障窗口都能击穿，没有第二道防线就是裸奔。
  • "靠数据库事务保证"——单行热点加连接池排队，DB 先死于锁而不是数据错。

AI 破绽自查：AI 能背全漏斗，但给不出"放行倍数是库存 2 倍"这种拍过板的数，也说不出"热点行分段没做"——你的答案里必须有这两句。

追问链

先自己心里答 10 秒，再展开对照。

追问一：Redis 预扣成功了，MQ 消息丢了怎么办？

考察意图：跨中间件的中间态意识——秒杀真正的难点不在峰值在缝隙。

答到什么程度算过关：先承认预扣与发消息没有跨组件事务，再给三选一：本地消息表（预扣流水与消息落同一 DB 事务，后台投递）、事务消息（RocketMQ 半消息 + 回查）、对账补偿（定时比对预扣流水与订单，超时未下单回补库存）。关键细节：回补必须幂等（带预扣流水号），且回补前先校验订单确实不存在——否则消息只是迟到，回补就变超卖。能说出"宁可少卖 2 分钟，不可超卖 1 件"的取向，过关。

追问二：一人一单怎么实现？集群下会不会放进两个？

考察意图：原子性边界从库存扩展到业务规则。

答到什么程度算过关：判断与扣减必须在同一个 Lua 脚本里（SISMEMBER 查集合 + SADD 加入 + DECR 库存一次完成），拆成两条命令就有并发缝隙。但 Redis 是缓存语义，最终防线是 DB 唯一索引（user_id + sku_id），插入冲突即失败并回补。面试官若追风控维度，补设备指纹与黑名单的布隆判断。能把"Redis 挡量、DB 唯一约束兜真相"说出层次，过关。

追问三：如果库存是 10 万件、流量 100 万，方案变吗？

考察意图：换量级重算的能力——背方案与做设计的分界线。

答到什么程度算过关：会变，两处。其一，放行倍数不能再用 2 倍（放 20 万 QPS 等于不设防），要按时段与真实转化率调；其二，落库量到万级 TPS，热点行分段从"不值得"变成"必须"——10 万库存拆 100 段，段内仍条件更新，段间不均用借段与回收，消费者按段并行。能现场把比例重算一遍而不是沿用上一题答案，就是会做设计的人。
