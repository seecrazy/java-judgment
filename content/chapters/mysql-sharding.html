工作场景

订单表 2.3 亿行，MySQL 8.0 主从半同步，单实例 32C128G。大促压测预估写入峰值 4500 QPS，DBA 提交分库分表方案：16 库 64 表、按 user_id 哈希、双写迁移，工期两个月、6 人投入。CTO 在评审会上只问了一句：“瓶颈的证据是什么？有没有更便宜的路？”可选路径：

  • A. 按方案干：两个月换一套能扛十年增长的架构
  • B. 先归档：一年以上已完成订单 1.6 亿行搬历史库
  • C. 读写分离扩容：统计查询全部赶去从库
  • D. 先量化四个维度，用数据决定动不动

判断框架

第一步 · 约束

订单是核心链路：双写迁移期间不能停机、不能错单；6 人两个月的机会成本是排期里的另外三个需求；团队没有 sharding 中间件运维经验；产品愿意配合改交互（历史订单进“查历史”入口）——这条最后谈下来，选项的天平就偏了。

第二步 · 关键认知

“单表过亿就该分”是行数焦虑，不是瓶颈证据。InnoDB 是 B+ 树，2.3 亿行、行宽约 200B 时树高才 4 层，点查只是多一次页比较。真正会到顶的是四个可量化维度：写 QPS、连接数、磁盘、buffer pool 命中率。量化结果：写峰值 4500 QPS（单实例压测上限 8000+，余量 40%）；磁盘 58%；命中率 99.2%。真到顶的是两处：应用集群扩容后 Threads_connected 1500 逼近 max_connections=2000；运营多条件统计把从库 CPU 打到 90%。瓶颈不在行数，在访问方式。

第三步 · 选项与代价

B 归档最便宜，两天上线；代价是查一年前订单要走历史入口，交互要改。C 读写分离一周；代价是复制延迟下读到旧数据，要业务确认容忍度。还有一层业务改写比任何技术手段都便宜：运营“实时看板”砍掉一半没人看的指标、T+1 报表移进数仓——直接消掉 40% 的大查询。A 分库分表真能换写入水平扩展，但代价清单最长：sharding key 选定难回头、跨片查询要广播或异构索引、全局 ID、分布式事务面扩大、两个月工期加双写风险。

第四步 · 押注与复盘

押 B + C + 业务改写，分库分表挂起，并写死重启条件。结果：归档 1.6 亿行后单表回到 7000 万，buffer pool 命中率回升到 99.8%；连接治理（应用侧连接池收敛到每实例 20）后 Threads_connected 降到 600；从库 CPU 峰值从 90% 降到 45%。两个月工期省下，团队一个季度交付了三个需求。复盘沉淀一张“重启条件卡”：单表回到 2 亿行、写 QPS 实测过 8000、连接治理后仍到顶——命中任一，分片评审自动启动，不用再吵。

被否决选项的胜场

分库分表这次被否决，但它的胜场很清晰：写入实测触顶且无法靠归档减负、数据没有自然冷热边界（日志流水表不能归档）、未来三年增长可预期——这时两个月工期换十年水平扩展就是划算的，很多大厂交易库就是这么走的。NewSQL（TiDB）同理：免应用改造、弹性扩缩、团队没有分片中间件经验且有平台组兜底运维时，它是好答案；代价是一套新运维栈和不同的延迟模型。否决它们不是它们不好，是这次的瓶颈证据不支持。

回到工位

明天上班，为“该不该分”收集四个数字：

  1. 写 QPS：SHOW GLOBAL STATUS LIKE 'Com_insert'（含 update/delete 合计）按秒差值，对比自己压测出的单实例写上限——别拿网上“2000 万行”的经验值当线，那是别人行宽和索引数的答案。
  2. 连接：Threads_connected 对 max_connections，再核对各应用连接池 maxActive 之和是否远超实例上限——连接治理常常比分库便宜一个数量级。
  3. 磁盘增长曲线 + 命中率：Innodb_buffer_pool_read_requests 与 Innodb_buffer_pool_reads 之比算命中率，低于 99% 先查是不是大查询污染，不是急着扩。
  4. 把四个数字连同“重启条件卡”写进评审文档。要问业务的一句话：“一年前的订单还有多少人在页面里翻？愿意为它多点一次‘查历史’吗？”——这个答案决定 1.6 亿行能不能搬走。

面试怎么答

面试官的三种问法

  • “订单表 2 亿行了，怎么设计？”（系统设计开场，多数人直接跳进分片方案）
  • “什么情况下不该分库分表？”（高级岗真正的分水岭）
  • “分片键怎么选？买家和卖家都要查订单怎么办？”（考分片的真代价）

好回答的结构

第一句先反问瓶颈证据，再给便宜方案的阶梯：归档 → 冷热分离 → 读写分离 → 垂直拆，分片放最后并主动列代价清单和触发条件。“我们当时没做 X 因为 Y”在这里价值最高。

60 秒示范：“遇到这个题我先要瓶颈证据。我们的订单表 2.3 亿行，DBA 提了 16 库 64 表方案，评审时量化发现：写峰值 4500 QPS 而单实例压测上限 8000+，磁盘 58%，buffer pool 命中率 99.2%——真正到顶的只有连接数 1500 逼近上限，和运营统计把从库 CPU 打到 90%。所以没做分库分表：归档 1.6 亿行冷订单，单表回到 7000 万；40% 的统计大查询砍进数仓；连接池收敛后连接降到 600，从库 CPU 峰值 45%，省下 6 人两个月。同时写死重启条件：单表回 2 亿行或写 QPS 实测过 8000，分片评审自动启动。如果证据反过来是写入触顶，我会坚决分：分片键选 user_id，卖家维度用异构索引表解决。”

翻车回答

  • “亿级必须分库分表”——把经验值当证据，追问一句“写 QPS 多少”就塌。
  • 上来就讲 ShardingSphere 怎么配——工具先行，没有量化的位置，也没有业务改写的位置。
  • 分片方案只讲好处不讲代价（跨片查询、全局 ID、分布式事务、双写迁移）——说明没真正上过线。

AI 破绽自查：AI 会把归档、读写分离、分片并列各写一段。真实工程师的答案有顺序（便宜的先做）、有数字、有“我们当时否决了分片，因为瓶颈在连接和统计查询不在写入”。

追问链

先自己心里答 10 秒，再展开对照。

追问一：分片键选 user_id 还是 order_id？跨片查询怎么办？

考察意图：分片真代价的第一现场——维度选择决定未来所有查询的形态。

答到什么程度算过关：按最高频查询维度选：C 端查自己的订单选 user_id，一个用户全部订单落一片，点查和翻页最优；代价是卖家、运营维度全变跨片。跨片三板斧按代价排序：入口带分片键（订单详情页用 order_id 查时，先查 order_id → user_id 的映射路由）；次要维度建异构索引表（按卖家维度再异构一份）；复杂多条件走 ES 或数仓回填，接受秒级延迟。全局 ID 用雪花或号段模式，雪花要处理时钟回拨。答不出“异构索引”四个字，就没真做过分片。

追问二：真要分，2.3 亿行怎么不停机迁过去？

考察意图：方案落地能力——从评审会的 PPT 到生产之间隔着什么。

答到什么程度算过关：五步且每步可回滚：① 存量全量迁移（DTS / mysqldump 低峰跑）；② 增量用 binlog 订阅（canal）追平；③ 应用开双写，写老库为主，新库写失败进补偿队列不阻塞主链路；④ 对账（行数 + 抽样 + 业务对账任务）一致后灰度切读，1% 到 100%；⑤ 切写，老库保留两周回滚窗口。要点：迁移前先统一 ID 生成规则，对账是切流量的前置条件。能主动说出“双写期间新库失败不拖垮业务、靠补偿追平”，过关。

追问三：为什么不用 TiDB 直接替换，免掉分片改造？

考察意图：技术选型的边界感——NewSQL 不是免费午餐。

答到什么程度算过关：先给 TiDB 赢面：MySQL 协议兼容、应用免改造、水平扩展与弹性、TiFlash 让大表分析免另建数仓。再给代价：一套新运维栈（PD / TiKV / TiFlash 及其监控）要人学和值班；高并发点查延迟通常高于同配置 MySQL（Raft 多副本提交）；小事务吞吐有折损。判断式落在组织而不只在技术：写入真到顶 + 团队无分片运维经验 + 有平台组兜底 → TiDB 值得；否则 MySQL 便宜方案阶梯仍是第一选择。能说出“这取决于运维组织，不只取决于技术”，加分。
