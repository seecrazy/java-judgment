工作场景

支付服务偶发下单失败，每天 20~50 笔、失败占比 0.3%，日志只有一行“下单异常: null”——异常的 message 恰好是 null，堆栈没打出来。测试环境无法复现，正值晚高峰不能重启，加日志发版最快要等明早。风控在催。可选路径：

  • A. 提交加日志的版本，明早看结果
  • B. 摘掉一台机器做“调试式”排查
  • C. Arthas attach 到线上实例，watch 条件抓失败现场
  • D. jstack / jstat / jcmd 内置工具全套先扫一遍

判断框架

第一步 · 约束

晚高峰不能重启、摘机器会丢容量；操作走堡垒机、全程留痕；watch 的输出可能带卡号、手机号、金额——脱敏是硬约束；字节码增强有开销，热路径不能裸挂。所以工具不是“能不能用”，是“以什么姿势用多久”。

第二步 · 关键认知：工具位次

进程级问题（CPU、GC、线程、死锁）用内置零侵入工具先答——jstack、jstat、jcmd、arthas 的 dashboard/thread 也属这一档；方法级问题（变量长什么样、分支走没走、时间花在哪层）才轮到字节码增强：watch 看数据，trace 看耗时分布，tt 先录后看适合守不到的偶发，profiler（async-profiler）采样看全局热点。工具放大判断，不替代判断——上工具之前，必须有一句可证伪的假设。

第三步 · 选项与代价

A 等发版：最稳，但今晚无解，而且没有假设时连“该在哪个方法打什么日志”都不知道。B 摘机复现：丢容量，且本地没有线上那份真实数据，基本靠运气。C watch：能拿到案发现场，代价是增强开销与脱敏责任——条件必须带、-n 限次必须带。D 内置全套：半小时排除资源型根因，答不了“参数进方法时是什么样”，但它是 C 的前置：先证明问题不在进程层，增强才有意义。

第四步 · 押注

D 的 30 分钟先行：dashboard、thread、GC 指标全部平稳，线程池没满、没有死锁——排除进程级。然后上 C：watch com.pay.order.OrderService create '{params, throwExp}' 'throwExp != null' -x 2 -n 3，挂上 23 分钟抓到第一笔：params 里渠道金额字段是空串，throwExp 是解析异常且 message 为 null——这正是日志里那个“null”的来源。与上游一核对：渠道两周前改版，金额字段偶发空串。当晚只做止血（该渠道降权），正式修复走次日发版；顺手立规矩：log.error 必须把异常对象传进去，不许只打 getMessage()。retransform 热修当时评估过没做——改动带分支逻辑，又不满足“有快速回滚预案”这个前提。

第五步 · 复盘

沉淀一页线上诊断 playbook：先内置后增强、条件必带、-n 限次、输出脱敏、用完必须 stop（重置增强类，不是关掉会话就走）。日志规范同步清零“只打 message 不打堆栈”的用法。

被否决选项的胜场

A（加日志重发）在问题高频、容易复现，或公司安全红线禁止字节码增强（银行、券商常见）时就是唯一正解，而且日志是长期资产，这次否决它只因“今晚要答案”。B（摘机复现）在问题与数据规模或真实流量相关（大客户请求、缓存击穿类）时可能是唯一复现路径。热更新 retransform 在“方法体级小改动 + 等不及发版 + 有审计和回滚”三条同时满足时是合格的止血——这次只差第三条，就不该用它。

回到工位

今天在预发把三条命令各跑一遍，形成肌肉记忆：

  1. watch com.xxx.OrderService create '{params, returnObj, throwExp}' 'throwExp != null' -x 2 -n 3——只在抛异常时触发，最多 3 次自动摘除。
  2. trace com.xxx.OrderService create '#cost > 100' -n 5——只看耗时超过 100ms 的调用树。
  3. tt -t com.xxx.OrderService create -n 5 录 5 笔，然后 tt -i 编号 看现场、tt -i 编号 -p 回放一次入参。

生产使用四条军规（写进团队 playbook）：条件必带，否则热路径全量输出等于自己打自己；-n 限次，抓到即走；输出里的卡号、手机号、金额不许外带，用完清屏；用完执行 stop 释放增强，别只退出会话。

顺手做一次工具位次体检，对照这张表检查自己团队的习惯：

工具回答的问题侵入度何时先上
jstat / jcmd / GC 日志堆与 GC 健康吗零第一步
jstack / thread线程在等什么、有没有死锁零CPU 高、阻塞时
dashboard / top进程级大盘零第一步
watch参数、返回、异常长什么样字节码增强有明确假设时
trace时间花在哪一层增强 + 统计耗时分布未知
tt那次偶发调用的现场录制期开销守不到现场
profiler全局热点在哪采样，很低整体变慢

最后问自己一句话：“下一次失败发生时，我最想看到哪一个变量？”答不出来，说明假设还没成型，先别上 watch。

面试怎么答

面试官的三种问法

  • “线上问题怎么排查？用过什么工具？”（一面，考体系）
  • “不能重启、不能发版，怎么看方法内部的数据？”（本题）
  • “Arthas 为什么能在运行时看到变量？原理是什么？”（二面，考深度）

好回答的结构

先说位次（进程级用零侵入工具，方法级才上增强）→ 给出你的假设 → 说命令与条件（这一步暴露你是真用过还是背的）→ 拿到的证据是什么 → 修复与规范沉淀。核心一句：watch 是用来验证假设的，不是用来碰运气的。

60 秒示范：“支付服务每天 20~50 笔失败，占比 0.3%，日志只有一行‘下单异常: null’。我先花 30 分钟用内置工具排除进程级问题——线程池、GC、死锁都正常；然后挂 Arthas：watch 下单方法，条件是 throwExp 不为空，限 3 次。23 分钟后抓到现场：渠道金额字段是空串，抛的是解析异常、message 恰好是 null，这就是日志里那个 null 的来源。当晚渠道降权止血，次日发版修复，并立了‘异常必须连堆栈打’的日志规范。retransform 热修我评估过没做——改动带分支且没有快速回滚预案，等 6 小时发版比引入不可审计的线上热改便宜。”

翻车回答

  • 罗列命令名像报菜名，说不出“我用 watch 验证了什么假设”——立刻降档为背过的。
  • watch 不带条件、-x 5 全量展开挂在热路径上——这不是诊断，是主动制造事故。
  • 只会 Arthas 不会 jstack / jstat，进程级问题也上增强工具——工具位次倒置，暴露没有方法论。

AI 破绽自查：AI 会把命令大全复述一遍。你的回答里必须有一个“当时挂了多久、抓到什么字段”的现场数字，和一句“热修我评估过没做”。

追问链

先自己心里答 10 秒，再展开对照。

追问一：watch 的条件表达式是什么引擎？有什么坑？

考察意图：细节使用深度，以及生产风险意识。

答到什么程度算过关：OGNL。坑至少说出两个：条件写宽了等于没写，热路径全量输出，先拿 -n 1 验证条件命中率；条件里不要调用有副作用的方法或重量级逻辑——它在每次调用都会被求值。能补一句“生产先在预发把表达式跑通”，更稳。

追问二：Arthas 为什么能在线上看到变量、改行为？原理讲一下。

考察意图：是只会用，还是理解机制边界。

答到什么程度算过关：Agent 的 attach 机制（agentmain）+ java.lang.instrument 的 retransformClasses，用 ASM 把观察逻辑织进目标方法字节码；watch 生效即改写目标方法，stop 时还原。由此推出边界：增强期间有额外开销、多次增强有累计风险、attach 失败的场景（权限、容器里无 JDK 工具链）要有预案。

追问三：热更新（jad/mc/retransform）到底能不能在生产用？

考察意图：对“止血”与“交付”的边界感，这题答错很扣分。

答到什么程度算过关：先说机制边界：retransform 只支持方法体级修改，不能加字段、加方法、改签名；再说工程边界：必须保留原 class 可回滚、操作留审计、事后必须走正式发版覆盖。结论一句：“热修是止血不是交付”——能主动说出这三个前置条件的人，才敢让他碰生产。

追问四：什么情况下应该停止诊断、直接下线处理？

考察意图：知道工具的尽头在哪，比知道工具本身更高级。

答到什么程度算过关：能举出“天生需要重启”的类别：要改启动参数的（开 NMT、换收集器、调 Xss）、类加载泄漏、确认死循环烧 CPU。正确顺序是：先保留现场（jstack、dump 落盘），再摘流量，再重启，最后离线分析。能说出“诊断已给出必须重启的结论还继续 attach，是徒增风险”，满分。
