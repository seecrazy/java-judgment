工作场景

大促领券，用户点一次“领取”，券到账 3 张。链路回放：网关 1 秒超时自动重试 2 次，MQ 消费者又在重平衡后重新投递——同一笔请求被完整处理 3 次。每张券成本 5 元，当天同类客诉 87 单。上游给的修复建议是“把重试关掉”，方向本身就错。可选路径：

  • A. 发券流水表加唯一索引，重复插入冲突即跳过
  • B. Redis setnx 前置挡板，key 为幂等键 + TTL
  • C. 状态机：领券单条件更新，只有 INIT 状态能发券
  • D. 治理上游：关重试、加防抖，别让重复请求进来

判断框架

第一步 · 约束

资金敏感：券有预算池，重复发就是资损，一张都不能多。峰值 3000 QPS（大促整点）。上游不可控：网关超时重试是平台默认行为，MQ 的 at-least-once 是协议属性，改不掉也不该改。幂等窗口：含死信重投在内，上游最长 24 小时内都可能再来一次。已有资产：领券本来就会落一张领券单记录，Redis 是现成的。

第二步 · 关键认知

重试放大流量，幂等吸收流量。分布式系统的超时是三态的：你发出请求后对端可能已经成功——超时不等于失败，重试是必然会发生的事。所以正确的投资方向不是消灭重试（D 方向反了），而是让“再执行一次”安全。另一个认知：幂等屏障要放在不可靠成分的下游——网络、网关、MQ 都不可靠，屏障必须贴近数据落点，DB 约束是最后也是最硬的一道。无退避的重试在对方过载时还会形成重试风暴，等于 DDoS 自己。

第三步 · 选项与代价

实现位正确性强度代价适用
DB 唯一索引 / 去重表最硬：并发安全、崩溃后仍有效一次额外写（毫秒级）、记录要归档资金类，一切的最后防线
状态机条件更新硬：依赖 DB 行锁原子性几乎为零（本来就要更新这行）有单据模型的业务动作
Redis setnx 挡板弱：主从切换丢 key、宕机要选 fail-open亚毫秒、挡量效果最好前置挡重复，只管性能

A 唯一索引是最硬的正确性，幂等键必须选准——本案用上游传的 request_id，没传的请求直接打回。C 状态机语义最准：UPDATE ... WHERE status='INIT' 条件更新天然原子，affected rows 为 0 就是“已处理过”，返回首次结果即可；代价是每个动作都要先有行记录，纯高频轻量动作用它偏重。B 挡板最快也最脆：把 99% 重复挡在 DB 之前，但 Redis 故障时防线就没了——它是性能优化，不是正确性来源，单独用等于把资金安全押在缓存上。D 治理上游只对了一半：客户端 bug 式的疯狂重试确实该限流，但正常网络重试是可用性保障，关掉它就是把可用性赌在网络永不抖动上。

第四步 · 押注与复盘

押 C 为骨架（领券单本来就存在，条件更新顺手）+ A 给发券流水加 UNIQUE KEY uk_request (request_id) 兜底 + B 挡板挡在入口，TTL 24 小时、与上游重试链路上限对齐。重试保留但加指数退避加 jitter：最多 3 次，1s/2s/4s 各带随机抖动。没上分布式锁——锁解决“同时进来”，解决不了“锁释放后重试再来”，锁崩了防线全失。复盘数字：上线后重复发券 0 起，挡板大促期间日均命中 40 万次，DB 冲突率 0.3%——分层各自在干活。

被否决选项的胜场

分布式锁的胜场：同一资源的并发热点收敛——缓存击穿单飞重建、秒杀库存行串行化，“抢到的人干活”这类场景它是对的；拿它做幂等是错位，因为重试在锁释放后还会再来。Redis 挡板单独用的胜场：重复无害、只是浪费的动作——埋点上报、报表回填、推荐重算，挡板省机器就够了，没必要为统计准确性改表。“上游不重试”的胜场：对明确的无效流量（客户端 bug、恶意重放）用限流和熔断治理——那是流量问题，不是一致性问题。分清这三类，选型才不串。

回到工位

今天就把写接口的幂等底账盘出来：

  1. 列出所有对外写接口（下单、发券、退款、回调），每个问一句并记下答案：“这个接口被同一笔请求调两次，会发生什么？”答不上来的，按资损排序今天改。
  2. 两条 SQL 先行：ALTER TABLE coupon_grant ADD UNIQUE KEY uk_request (request_id); 与 UPDATE coupon_grant SET status='GRANTED' WHERE id=? AND status='INIT';——并检查 affected rows 为 0 时是返回首次结果，而不是抛异常。
  3. 核对幂等窗口的一致性：Redis 挡板 TTL、去重表保留周期、上游最大重试间隔，三个数必须来自同一条推导链（窗口不小于上游最长重试链路），各拍各的脑袋就一定有缝。

面试怎么答

面试官的三种问法

  • “幂等怎么实现？”（一面标配，先看分层意识）
  • “Redis setnx 做幂等有什么问题？”（二面，考“正确性放哪一层”）
  • “调用下游超时了，这笔到底算成功还是失败？”（分布式认知的分水岭）

好回答的结构

先定幂等键（什么算“同一笔”），再按“正确性放 DB、性能放挡板”分层，最后补重试侧的退避与 jitter。一定要有一句“锁解决并发，不解决重复”。

60 秒示范：“我们大促重复发了券：一笔请求被处理 3 次，网关超时重试 2 次加 MQ 重平衡重投递，当天客诉 87 单。修复没有去关上游重试——超时不等于失败，重试是保命的，方向是把下游做幂等。押注三层：状态机条件更新做骨架，UPDATE 领券单 WHERE status='INIT'，affected rows 为 0 直接返回首次结果；发券流水加 request_id 唯一索引做最硬兜底；Redis 挡板挡在最前省 DB 压力，TTL 24 小时、与上游重试链路上限对齐——但它只是性能层，主从切换丢挡板也绝不会多发一张券。重试侧加指数退避 1s/2s/4s 带 jitter。上线后重复发券 0 起，挡板日均命中 40 万次。分布式锁评估过没上：锁释放后重试还会进来，锁解决并发不解决重复。”

翻车回答

  • “加个分布式锁就幂等了”——锁解决并发不解决重复，且锁自身故障时防线全失。
  • “Redis setnx 过期时间设 7 天就够了”——Redis 不是正确性来源，主从切换丢 key、宕机 fail-open 就破防。
  • “让上游别重试”——把可用性赌在网络永不抖动上，方向反了。

AI 破绽自查：AI 会把唯一索引、setnx、状态机各写一段但不分层。真实工程师必须说出哪层管正确性、哪层管性能，以及自己项目里挡板 TTL 是怎么推导出来的。

追问链

先自己心里答 10 秒，再展开对照。

追问一：超时之后到底该重试还是当失败？

考察意图：是否真正接受“超时三态”——这是所有幂等设计的起点。

答到什么程度算过关：超时意味着结果未知：对端可能成功、可能失败、可能还在执行。所以决策不在“这一次”，而在“下一次”：让操作幂等，然后放心重试；资金类再补一道对账闭环。能说出“我们不敢重试的根本原因不是网络差，是下游不幂等”，直接过关。

追问二：幂等键怎么选？上游没传 requestId 怎么办？

考察意图：幂等的语义设计能力，比实现手段更稀缺。

答到什么程度算过关：优先级：业务单号（支付流水号）高于协议强制 requestId（没传打回，倒逼上游），再高于请求指纹（body 哈希，防重放慎用），最后是语义组合键如 (用户, 券模板, 活动)——注意语义键会把“合法的第二次领取”也挡掉，只在业务确认一人一次时可用。能指出键的粒度就是幂等的粒度、选错粒度会误伤或漏放，才算理解。

追问三：去重记录要保留多久？和挡板 TTL 什么关系？

考察意图：幂等窗口的推导，考系统性而不是背配置。

答到什么程度算过关：窗口下限 = 上游最长重试链路（重试次数乘最大间隔，再加死信重投的跨度）。挡板 TTL 不小于窗口下限；DB 去重表保留期不小于挡板 TTL，账务类永久保留并进对账。三个数必须是同一条推导链。能举反例——“TTL 设 1 小时、上游 24 小时后死信重投，就是漏洞”——过关。

追问四：MQ 重复消费，幂等做在生产端还是消费端？

考察意图：MQ 语义认知——重平衡、生产者重发、Ack 丢失都会造成重复。

答到什么程度算过关：只能做在消费端。RocketMQ/Kafka 主流配置都是 at-least-once：消费者处理完还没 Ack 就崩，重启后消息重投；重平衡时未提交位移的消息也会再来。生产端去重挡不住这些。消费端幂等 = 幂等键 + 落库唯一约束，处理逻辑设计成重复消费无副作用。顺带说出顺序消息与幂等的配合（同一业务键路由同一队列），属于加分。
