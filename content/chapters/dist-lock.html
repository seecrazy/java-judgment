工作场景

夜里 2 点的商户对账任务部署了 4 个实例，同一个 cron 各自触发，每晚重复执行 4 次。第二天运营反馈差异报表多了 2000 多行重复记录——实际差异只有 600 笔，重复跑的任务把同一批差异往表里插了 3 遍，下游补偿流程差点按重复行重复打款。团队拉会争论上 Redis 锁还是 ZooKeeper 锁，吵到一半没人回答最初的问题：这个任务重复执行，到底会出什么事？可选路径：

  • A. Redis 锁（Redisson），抢到锁的实例执行，其余跳过
  • B. ZooKeeper 锁：临时顺序节点 + 会话，崩溃自动释放
  • C. 调度中心路由单播，只派给一个实例执行
  • D. 不加锁：任务改造成可安全重跑，差异表补唯一约束

判断框架

第一步 · 约束

先把任务拆开看：核对阶段天然幂等——重跑只是把同样的账再算一遍；差异落表阶段不幂等——差异表 (bill_date, merchant_order_no) 没有唯一索引，插几遍是几遍；后面的自动补偿在读差异表，重复行会被当真。另一个约束：团队没有 ZooKeeper 集群也没人运维过；Redis 在跑，Redisson 是现成依赖。结论先行：这是一个幂等临界区——锁弱一点，后果只是浪费机器；锁丢了，后果是重复计算，不会算错钱。

第二步 · 关键认知

选锁的第一个问题不是“Redis 还是 ZK”，是“锁保护的临界区幂等吗？”。幂等临界区，锁弱一点只是浪费——两个实例同时跑对账，结果照样正确；非幂等临界区，锁再强也不够——持锁线程一次长 GC 停顿就能让锁超时释放，第二个持有者进场，第一个恢复后继续写。所以分布式锁从来不是正确性的来源，正确性来自幂等，锁只是减少无效重复的性能优化。这句话决定整章的选型顺序。

第三步 · 选项与代价

A（Redisson）最顺手，但失败面要认清：主从异步复制下，客户端在 master 拿到锁、还没同步出去 master 就挂了，故障切换后别的实例照样拿到锁；另外显式传 leaseTime 会关掉看门狗——看门狗只在 lock() 不传时长时生效，默认 30 秒、每 10 秒续期。B（ZK）是 CP：临时顺序节点 + 只监听前驱，会话断开自动释放，不依赖时钟租约；代价是为一个幂等任务引入整套 ZK 运维，会话超时调短了误释放、调长了崩溃后别人干等。C（调度单播）把“只跑一次”上移到调度层，但多数调度器在故障转移时是至少一次语义，仍可能双跑——它减少浪费，不提供正确性。D（可重跑）把正确性放回 MySQL：唯一索引挡住重复插入，DuplicateKey 当“已处理”跳过，不依赖任何中间件。

第四步 · 押注与复盘

押 D 为主、C 为辅：差异表补 UNIQUE KEY uk_diff (bill_date, merchant_order_no)，任务改成可重跑；调度路由改单播，少跑三次是省资源不是保正确。A 保留给一个真正的高频热点（缓存重建单飞挡板）；B 和 RedLock 都没做——为幂等临界区引入强一致组件是负资产，RedLock 的多实例多数派也买不到非幂等场景想要的正确性。复盘数字：上线一个月重复差异 0 起；副作用是正向的——白天敢手动重跑对账了，修数从等次日凌晨缩到 10 分钟。

被否决选项的胜场

ZK 锁的胜场很明确：低频、非幂等、又改不动的老系统——每分钟几十次的遗留批处理，代码动不了只能靠外部互斥，且公司本来就有 ZK（Kafka 老版本依赖的那套），临时节点锁是当时最稳的选择；选主场景它更是标准答案。Redis 锁的胜场是高并发短临界区的流量挡板：防缓存击穿单飞重建、防重复提交的第一道闸。RedLock 很难单独找到胜场——5 个实例的运维换来的正确性承诺，在 GC 停顿和时钟跳变面前依然站不住（Kleppmann 与 antirez 2016 年那场争论的工程结论）。这次全没选，是因为对账任务的数据特征用一行唯一索引就解决了。

回到工位

明天上班，先盘点再动手：

  1. 把多实例部署的定时任务全找出来：grep -rn "@Scheduled\|@XxlJob" --include="*.java" .，对照部署副本数，圈出“副本数 > 1 且会同时触发”的任务清单。
  2. 对每个任务问一句话并记录答案：“这个任务重跑一次，结果会怎样？”——答“没影响”的走可重跑路线；答“会重复扣款/发券”的进下一问：“幂等键是什么？”没有幂等键的任务，比没有锁的任务危险得多。
  3. 检查现存的 Redisson 用法：grep -rn "lock(" --include="*.java" .，凡是显式传了 leaseTime 的，确认持锁时长 100% 可控——否则看门狗已被关掉，业务一旦比预期慢，锁会在执行中途过期。

面试怎么答

面试官的三种问法

  • “Redis 分布式锁和 ZooKeeper 的怎么选？”（二面标配，考选型维度）
  • “持锁的服务 GC 停顿了 20 秒，锁会怎样？”（考失败面，这是分水岭）
  • “你们线上哪里用了分布式锁？”（考真实经历，背题者在这里断电）

好回答的结构

开口第一句先问锁保护的是什么操作（幂等吗），再按“幂等选轻锁、非幂等上数据层约束”给结论，最后主动交代所选中锁的失败面（主从切换、看门狗边界）。中间件优劣对比放最后一句带过。

60 秒示范：“我们对账任务 4 个实例每晚重复跑 4 次，差异表被插了 3 遍重复数据。复盘没先吵 Redis 还是 ZK，先确认了临界区：对账重跑只是浪费，差异落表补一个唯一索引就安全，所以主修复是一行 UNIQUE KEY 加调度单播，锁都没上。Redisson 我们只用在缓存重建挡板这种幂等临界区，并且知道它两个坑：主从切换可能丢锁；显式传 leaseTime 会关掉看门狗——看门狗默认 30 秒、每 10 秒续期，只在调 lock() 不传时长时生效。ZK 锁评估过没上：为幂等任务引入强一致组件是负资产。真到非幂等临界区，比如重复打款，锁再强也挡不住 GC 停顿后的双持有者，正确性必须落到幂等键加 fencing token 或数据库条件更新上。”

翻车回答

  • 上来就背“Redis 性能好、ZK 一致性强”，全程不问锁的是什么——没有选型维度。
  • “Redisson 有看门狗，不会出问题”——看门狗管续期，管不了主从切换丢锁，还会被显式 leaseTime 关掉。
  • “用 RedLock，5 个节点大多数加锁成功，最安全”——把它用在非幂等临界区恰恰是最危险的组合。

AI 破绽自查：AI 会把 Redis/ZK/etcd 三方对比写得滴水不漏但不押注。真实工程师必须说出“我们哪个任务没上锁、为什么一行唯一索引就够了”。

追问链

先自己心里答 10 秒，再展开对照。

追问一：Redisson 看门狗的机制是什么？什么时候会失效？

考察意图：是否真用过 Redisson，还是只在简历上写过。

答到什么程度算过关：不传 leaseTime 时启用：默认锁 30 秒（lockWatchdogTimeout），后台每 10 秒（约 1/3）续到 30 秒，进程活着就一直持有。失效面三条：显式传了 leaseTime 直接没有看门狗；进程假死（长 GC、CPU 饥饿）超过剩余租约，锁照样过期、别人进场；master 挂在锁同步到副本之前，故障切换后锁直接消失——看门狗续的是它看到的那把锁。能补一句“所以我们只把它用在幂等临界区”，说明理解锁的定位。

追问二：RedLock 争论到底在争什么？工程结论是什么？

考察意图：有没有读过一手争论（Kleppmann 与 antirez），以及能否收敛成工程决策。

答到什么程度算过关：Kleppmann 的核心：RedLock 的安全性依赖时钟不跳变、进程停顿可控，而 GC 停顿和时钟跳变恰恰是真实系统常态；没有 fencing token，客户端停顿恢复后仍会拿着旧锁写，多实例多数派解决不了这个。antirez 反驳时钟可管理，但没有推翻停顿问题。工程结论一句话：多数派加锁买到的是可用性，不是你要的正确性——非幂等临界区要 fencing token 加存储层拒绝旧 token，或者直接用数据库约束；幂等临界区单实例 Redis 锁就够，RedLock 两头不占。

追问三：fencing token 怎么落地？没有 ZK 怎么做？

考察意图：从概念到实现的距离——多数人背得出名词，落不了地。

答到什么程度算过关：锁服务每次发锁附带单调递增 token，存储侧只接受比已见过的更大 token 的写。ZK 可以用事务 zxid 或顺序节点序号当 token；Redis 的 token 在主从切换后单调性难以保证，这是它做不了 fencing 的根因。没有 ZK 的落地替代：MySQL 乐观锁条件更新 UPDATE account SET balance = balance - 100, version = version + 1 WHERE id = ? AND version = ?，affected rows 为 0 就拒绝——本质是让存储层自己当裁判。答出“最后兜底永远是存储层条件”才算过关。

追问四：不用锁，防重复下单怎么防？

考察意图：能否把锁、幂等、状态机三个工具放进同一个选择框架。

答到什么程度算过关：三道闸从外到内：客户端防抖是体验优化，不算数；服务端幂等键（客户端生成的 requestId）+ 订单表唯一索引，重复请求直接返回第一次的结果，这是正确性主体；并发下的状态机条件更新 UPDATE orders SET status = 'PAID' WHERE order_no = ? AND status = 'UNPAID' 兜住“两个都进来了”的情况。锁在其中的位置：只在热点收敛（同商品秒杀库存行）才值得上，而且上了锁仍要幂等——锁解决并发，不解决重复。能说出这句分工的，直接进高级档。
